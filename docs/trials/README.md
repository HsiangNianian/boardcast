# 目标用户试用（#36）

当前只有准备材料，尚未招募用户，也没有第二周留存或付费意愿数据。先用通过验收的候选安装包，
分别找做技术方案评审和论文组会的人；两类合计 10～20 人，每人参加一次访谈、在第二周回访。
联系方式由项目负责人私下保存，仓库只使用匿名编号。不要把邀请发出数当成安装数或使用数。

可以直接复制的邀请：

> 我在做 boardcast：开会时把讨论整理到白板，并生成会后摘要。想找做技术方案评审或论文组会的朋友，
> 在自己的真实会议里试两周。第一周选一场会试用，第二周再告诉我有没有继续用；每次花几分钟记下
> 哪一处板书或摘要不准确。遇到问题可以发不含会议文字和音频的收音诊断；会议内容由你自己保留。
> 方便的话，我们再约一次简短访谈。现在主要想知道它在真实工作里是否有用。

不要自动发送这段邀请；由项目负责人选择联系人和渠道。使用 `cohort.csv` 记录每人的状态，
日期和数据没有拿到时留空，不填 0。每次使用记包版本、系统、模型、会议类型/时长、是否完成和最大问题。
访谈按下面的问题记原话和观察，避免把“愿意试试”解释为愿意付费：

- 用在哪种会上？目前怎么记录、会后怎么整理？
- 哪次板书、连线、说话人或摘要出错？你是修改、忽略，还是放弃？为什么？
- 第二周是否再次使用？用了几场？没再用的原因是什么？
- 你是否愿意付 29～49 美元买断？愿意／不愿意／不确定，原因是什么？这是访谈意愿，不是付款。
- 有什么事情必须修好，你才会把它带进下一场会？

结论报告必须带分母：邀请、安装、第一周实际用过、完成第二周观察的人数分别是多少；
第二周回访未完成的人不能归入“不再使用”。分别报告两类用户的重复使用与明确愿意付费人数。
把最多见的失败按“是否阻止继续使用”排序；如果连线错误居首，再依据 #6 决定模型方向。
最后说明目标用户/定价是否需要调整，以及先修哪个问题还是继续准备上架。

试用前先完成 [Mac 收音与长会验收](../../eval/macos/README.md)；开发者签名/公证和首次安装边界仍由 #11 跟踪。
收集真实数据后才填写结论和更新 #36 的完成状态。
